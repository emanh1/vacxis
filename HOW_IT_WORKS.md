# HOW IT WORKS

This document describes the test-dataset review pipeline that lives on the
`test-dataset-review` branch.

## Purpose

The golden evaluation dataset (`test_dataset.json`, `test_dataset_masked.json`)
is generated by an LLM and therefore needs an independent QA pass before it
can be trusted as a reference set. The pipeline splits the datasets into small
review units and audits every record with a separate LLM, combining cheap
deterministic checks with model judgement.

## Stage 1 — Split

`tools/split_test_dataset.py` splits each source dataset into three
consecutive, near-equal, order-preserving parts under `test_data_review/`:

| Source | Records | Parts |
| --- | --- | --- |
| `test_dataset.json` | 300 | 100 / 100 / 100 |
| `test_dataset_masked.json` | 726 | 242 / 242 / 242 |

The split is deterministic, so a part is always the same slice of the same
source file. Concatenating the three parts of a dataset reproduces the source
exactly.

```bash
uv run --no-sync python tools/split_test_dataset.py
```

## Stage 2 — Review

`tools/review_test_dataset.py` audits every record of every part.

### Configuration

Three environment variables configure the endpoint:

| Variable | Meaning |
| --- | --- |
| `TESTDATA_API_KEY` | Credential sent to the endpoint |
| `TESTDATA_BASE_URL` | Base URL of the OpenAI-compatible API |
| `TESTDATA_MODEL` | Model used to audit |

Missing variables abort the run with an explicit message.

```bash
uv run --no-sync --env-file .env python tools/review_test_dataset.py
```

### Pipeline

1. **Select parts.** Every `*.part*.json` in the output directory, excluding
   `review_report_*.json` (the reports live in the same directory and would
   otherwise be loaded as if they were parts).
2. **Load the checkpoint** (`review_checkpoint.jsonl`). Rows already reviewed
   are reused; nothing is re-requested from the model.
3. **Allocate the sample** when `--sample N` is given, proportionally across
   the parts. A part allocated zero records is skipped and still produces an
   empty report, so the summary stays complete.
4. **Review each record.** One API call per record, executed by a
   `ThreadPoolExecutor` with `--workers` concurrent calls.
5. **Assemble the verdict** for each record: deterministic checks, semantic
   checks, issues, failed check names, and a `PASS`/`FAIL` verdict.
6. **Checkpoint** every successful row to the JSONL file as it completes, so
   an interrupted run resumes where it stopped.
7. **Write** one `review_report_<part>.json` per part plus a consolidated
   `review_summary.json`.

### Criteria

Eleven checks run per record: seven deterministic (local, no API cost) and
four semantic (model).

**Deterministic checks**

| Check | Passes when |
| --- | --- |
| `reference_answer_present` | `REFERENCE_ANSWER` is a non-empty string |
| `answerability_label_valid` | `ANSWERABILITY` is one of `ANSWERABLE`, `PARTIALLY_ANSWERABLE`, `UNANSWERABLE` |
| `query_present` | `QUERY` is a non-empty string |
| `citations_resolve` | every `[CHUNK_ID]` in `REFERENCE_ANSWER` names one of the record's `RELEVANT_CHUNKS` |
| `claim_evidence_present` | every `CLAIM_EVIDENCE_MAP` entry has both a `chunk_id` and an `evidence_quote` |
| `claim_chunk_ids_valid` | every claim's `chunk_id` exists in `RELEVANT_CHUNKS` |
| `claim_quotes_verbatim` | every `evidence_quote` appears literally in the chunk it cites |

**Semantic checks** (the model, one call per record)

| Check | Question it answers |
| --- | --- |
| `answerability_match` | Does the label match the evidence? `ANSWERABLE` = chunks fully answer the query, `PARTIALLY_ANSWERABLE` = chunks cover only part of it, `UNANSWERABLE` = chunks do not answer it at all |
| `answer_grounded` | Is every factual statement in `REFERENCE_ANSWER` supported by the chunks, with nothing invented or extrapolated from outside them? |
| `query_type_match` | Does the query really ask what `QUERY_TYPE` claims it asks? |
| `query_wellformed` | Is the query a single, self-contained, unambiguous Vietnamese question naming a concrete vaccine or topic, with no placeholder, empty field, or instruction aimed at the assistant? |

The model also reports issues with a severity: `critical` (wrong
`ANSWERABILITY` label, hallucinated answer, wrong citation), `major` (wrong
`QUERY_TYPE`, ambiguous query), `minor` (small formal issues).

A record is `FAIL` when any of the eleven checks failed, otherwise `PASS`.
`failed_checks` names exactly which ones.

### Model I/O format

The endpoint returns empty content whenever `response_format` is set (both
`json_schema` and `json_object`), so the review speaks plain text in both
directions and no JSON is involved.

The record is rendered as labelled plain text — query, query type,
answerability, every chunk with its id and body, the reference answer, and the
claim/evidence map as `- claim` / `chunk_id` / `evidence_quote` lines.

The model is asked to answer in this shape:

```
answerability_match: PASS | FAIL - <giải thích>
answer_grounded: PASS | FAIL - <giải thích>
query_type_match: PASS | FAIL - <giải thích>
query_wellformed: PASS | FAIL - <giải thích>

ISSUE <critical|major|minor> <check>: <mô tả lỗi>
```

`parse_review_reply` tolerates surrounding prose, leading list markers
(`-`, `*`, `•`), case variants of the check names, and a missing
`- detail` suffix. A line it cannot parse is dropped, and the affected check
then fails — the parser never turns a bad reply into a pass.

Every stored row keeps the model's raw reply in `raw_reply`, so a parser
miss never loses the review text.

### Options

| Flag | Effect |
| --- | --- |
| `--out-dir DIR` | Directory holding the parts and receiving the reports (default `test_data_review/`) |
| `--workers N` | Concurrent API calls (default 8) |
| `--timeout SECONDS` | Per-request timeout (default 300) |
| `--retries N` | Retries per record after a failed call (default 2) |
| `--limit N` | Review only the first N part files |
| `--sample N` | Review about N records in total, spread proportionally across the parts |
| `--tag NAME` | Suffix the checkpoint, report and summary filenames, so a sample run cannot overwrite a full run's artifacts |

### Outputs

| File | Contents |
| --- | --- |
| `review_checkpoint.jsonl` | One JSON row per reviewed record, appended as it completes |
| `review_report_<part>.json` | Per part: record counts and the full result rows |
| `review_summary.json` | Per part: `records`, `passed`, `failed`, `errors` |

## Reading the results

- `claim_quotes_verbatim` fails on roughly 15% of records. This is by design:
  the check demands a literal substring, and the failing quotes appear in no
  chunk of the record at all. They are genuine paraphrase defects — the
  generator wrote a summary where a verbatim excerpt was required.
- `errors` counts records whose API call failed, not records that failed
  review. Errored rows are not checkpointed, so a resume retries them; a
  record that fails every time is retried on each resume.
- In the first live sample, `answerability_match` and `answer_grounded` failed
  on seven of the nine records that received a model reply, which points at
  systemic labelling and grounding problems rather than isolated typos.

## Known limits

- The reference answer is checked for *groundedness*, not for clinical
  correctness. A medically wrong but chunk-supported answer passes.
- The chunks are not validated against the source corpus, so a chunk that
  does not really come from the vaccine's document would pass as long as the
  answer matches it.
- The model never sees `QUERY_SOURCE`, `VERIFIED`, `ADJUDICATED` or
  `EVIDENCE_COMPLETENESS`, and no check ties the chunks to the document named
  in `RELEVANT_DOCS`.
